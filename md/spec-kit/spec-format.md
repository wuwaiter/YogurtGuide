# SPEC 長什麼樣

一個需求（或一個專案）要有兩份 SPEC，回答不同的問題，各由不同階段產出：

| | 需求規格 `checklist.md` | 技術規格 `plan.md` |
|---|---|---|
| 回答 | 做什麼（What）、為什麼（Why） | 怎麼做（How） |
| 產出階段 | 2 需求分析、3 需求確認 | 4 編寫計畫 |
| 讀者 | 需求方、SPEC_BOSS、SPEC_SA | SPEC_SA、實作的 AI Agent |
| 不能出現 | 框架、資料庫、套件、檔案路徑 | 新需求（發現缺漏要退回 3） |
| 通過條件 | 沒有 `[待確認]`、檢查清單全勾 | 原則檢查全過、每條需求都有落點 |

範例：`example-yogurtguide/checklist.md`、`example-yogurtguide/plan.md`。

---

## 共通格式

1. **Markdown**，一個需求一個資料夾：`specs/<編號>-<短名>/`。
2. **檔頭**固定 5 欄：名稱、版本、狀態（草稿／確認中／已確認／已取代）、日期、來源（需求從哪裡來）。
3. **編號不重用**，刪掉的編號標「已移除」並留著：
   - 需求 `R-01`、驗收 `AC-01-1`、非功能 `NFR-01`、邊界 `E-01`、成功標準 `SC-01`
   - 技術決策 `D-01`、介面 `IF-01`、任務 `T-001`
4. **可追溯**：`R-xx` → `plan.md` 的落點 → `T-xxx` → 測試。任何一層找不到上一層，就是多做；找不到下一層，就是漏做。
5. **不確定的寫 `[待確認：問題]`**，不准自己補答案。
6. **改版**：已確認的 SPEC 要改，版本號加 1，在檔尾「變更紀錄」寫改了什麼、為什麼，並退回需求確認。

## 需求規格 `checklist.md` 的段落

| # | 段落 | 內容 | 必填 |
|---|---|---|---|
| 1 | 背景與目的 | 為什麼要做、不做會怎樣，3–5 句 | ✓ |
| 2 | 使用者與角色 | 誰會用、各自要達成什麼 | ✓ |
| 3 | 範圍 | 這次做／不做（不做的要寫，避免被默默加進來） | ✓ |
| 4 | 需求清單 | 每條 `R-xx`：一句話、為什麼、優先序（P1/P2/P3）、輸入、輸出、失敗時、驗收 Given/When/Then | ✓ |
| 5 | 資料項目 | 要記哪些東西、彼此關係、唯一識別；不寫資料表或欄位型別 | 有資料才填 |
| 6 | 狀態與順序 | 狀態清單、允許的轉換、什麼完成前不能做什麼 | 有流程才填 |
| 7 | 邊界條件 | 空值、零、負數、超過上限、格式錯、重複送出、日期或時區交界、離線、外部服務失敗 | ✓ |
| 8 | 非功能需求 | 效能、離線、隱私與敏感資料、權限、稽核、授權、語言 | ✓ |
| 9 | 成功標準 | 可量測，不提技術（「3 秒內看到」而不是「API 200 ms」） | ✓ |
| 10 | 假設與待確認 | 假設逐條標「假設」；問題標 `[待確認]` | ✓ |
| 11 | 品質檢查清單 | 見下方，SPEC_BOSS 逐項打勾 | ✓ |
| 12 | 變更紀錄 | 版本、日期、改了什麼 | ✓ |

### 一條需求的寫法

```markdown
### R-03 菌粉卡片缺資料時顯示固定文字（P1）

- 為什麼：讀者要分得出「查不到」和「產品沒有」。
- 輸入：一筆菌粉資料。
- 輸出：卡片上的評價、菌種欄位。
- 失敗時：沒有評價 → 顯示「沒有評價資訊」；沒有菌種 → 顯示「沒有菌種資訊」。
- 驗收：
  - AC-03-1 Given 一筆菌粉沒有評價，When 打開菌粉頁，Then 該卡片顯示「沒有評價資訊」。
```

### 品質檢查清單（每份 `checklist.md` 都要有）

- [ ] 每條需求都有「為什麼」與優先序
- [ ] 每條需求都寫了輸入、輸出、失敗時的結果
- [ ] 每條需求至少一個 Given/When/Then 驗收，且能單獨測
- [ ] 狀態轉換寫明先後順序，沒有「做到一半」的狀態
- [ ] 邊界條件逐類寫過（不適用的寫「不適用」）
- [ ] 敏感資料已標出：不能進 log、不能離開這台裝置或這個系統
- [ ] 成功標準可量測、不含技術名詞
- [ ] 範圍有寫「不做」
- [ ] 全文沒有框架、資料庫、套件、檔案路徑
- [ ] 沒有剩下 `[待確認]`

## 技術規格 `plan.md` 的段落

| # | 段落 | 內容 |
|---|---|---|
| 1 | 摘要 | 一段話：用什麼方式滿足哪些 R |
| 2 | 技術背景 | 語言版本、框架、儲存、測試、目標平台、部署、限制；不知道的寫 `[待確認]` |
| 3 | 原則檢查 | 逐條對專案 `AGENTS.md` 的原則：通過／違反（違反要寫理由與被否決的簡單做法） |
| 4 | 架構 | 元件圖（Mermaid）、每個元件負責什麼、不負責什麼 |
| 5 | 目錄結構 | 實際路徑，新增的標「新」 |
| 6 | 資料模型 | 實體、欄位、版本號、舊資料怎麼讀回（遷移） |
| 7 | 介面合約 | 檔案格式、API、事件；每個 `IF-xx` 寫輸入、輸出、錯誤 |
| 8 | 流程 | 每個主要流程一張圖：正常路徑＋每個失敗分支的結果 |
| 9 | 失敗處理 | 表格：失敗點、偵測方式、結果（保證不留半筆） |
| 10 | 安全與敏感資料 | 秘密放哪、誰能讀、什麼不能進版控或 log |
| 11 | 技術決策 | `D-xx`：選了什麼、放棄了什麼、為什麼 |
| 12 | 需求落點 | 表格：`R-xx` → 落在哪個元件／流程／介面 |
| 13 | 風險與待確認 | 會出事的地方、還沒定的事 |
| 14 | 變更紀錄 | 版本、日期、改了什麼 |

## 兩份之外

| 檔案 | 階段 | 內容 |
|---|---|---|
| `questions.md` | 3 需求確認 | 每題：編號、對應 R、問題、選項與建議、答案、答覆日期 |
| `tasks.md` | 5 任務拆解 | `T-001` 起，每項一個可驗證的小步驟 |
| `report.md` | 6 執行實作 | 每個任務的結果、測試輸出、偏離與原因 |

格式與範本見 `spec-kit.md`。
